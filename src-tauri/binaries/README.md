# Bundled sidecars

This directory holds the static FFmpeg binaries Hickeyfield ships. **Nothing here
is committed** — `.gitignore` excludes `src-tauri/binaries/*` apart from
`.gitkeep` and this file. Run the fetch script instead:

```sh
scripts/fetch-ffmpeg.sh              # this machine's target
scripts/fetch-ffmpeg.sh --all        # every shipping target
scripts/fetch-ffmpeg.sh --check      # verify what is already here
```

A build without a sidecar still compiles; it fails at the first export, with
`FfmpegError::NotFound` naming the file it looked for.

## Naming is not cosmetic

Tauri resolves `externalBin` by exact target-triple suffix. The file must be
named `ffmpeg-<triple>`, with `.exe` on Windows:

| target | file |
|---|---|
| `aarch64-apple-darwin` | `ffmpeg-aarch64-apple-darwin` |
| `x86_64-pc-windows-msvc` | `ffmpeg-x86_64-pc-windows-msvc.exe` |

Get the suffix wrong and `tauri build` fails with "binary not found" while the
file is plainly sitting right there. Inside the finished bundle Tauri renames it
to plain `ffmpeg`, which is why `hickeyfield_core::ffmpeg::locate` accepts both
spellings — checking only one works in dev and breaks in the shipped app.

## Static only

Use static builds. A dynamically linked FFmpeg cannot resolve its dylibs once it
is inside an `.app` bundle (Tauri discussion #9029), and the failure appears only
after packaging. Homebrew's ffmpeg is dynamic, so it is fine for running the
`--ignored` tests and wrong for bundling.

Confirm with `otool -L` (macOS) — only system frameworks should appear.

## Licence: the one thing to get right

Hickeyfield is AGPL-3.0-or-later. We ship a **GPL** FFmpeg, which is compatible:
FFmpeg's "or later" reaches GPL-3, and AGPL-3 §13 permits the combination
explicitly. `--enable-gpl` is required anyway, because libx264 is our software
encoder.

The two builds are not under the same GPL version, which is easy to miss and
matters for which licence texts ship:

| target | flags | effective licence |
|---|---|---|
| `aarch64-apple-darwin` | `--enable-gpl` | GPL-2.0-or-later |
| `x86_64-pc-windows-msvc` | `--enable-gpl --enable-version3` | GPL-3.0-or-later |

`--print-notice` states this per target, so `NOTICE` cannot drift from what is
actually in the bundle.

**`--enable-nonfree` makes a build legally unredistributable.** It looks and
behaves exactly like a legal one, so the only defence is to ask:

* `scripts/fetch-ffmpeg.sh` refuses to install such a build.
* `hickeyfield_core::ffmpeg::licence_check` asserts it at runtime and in CI, per
  the M3 exit criterion.

Never ship libfdk-aac. Several popular Windows "full" builds include it, which
is precisely what forces `--enable-nonfree`.

Obligations that come with this, and where each is met:

| obligation | where |
|---|---|
| record the exact configure flags | `NOTICE`, generated by `--print-notice` |
| ship FFmpeg's licence text | `LICENSES/GPL-2.0.txt` **and** `LICENSES/GPL-3.0.txt` — neither exists yet |
| written offer for the corresponding source | `NOTICE` |

## Two non-licence gates the script also enforces

* **libx264** — without it there is no software fallback when hardware encoding
  is unavailable, and the export just fails.
* **libfreetype** — without it the `drawtext` filter does not exist and every
  burned-in caption fails at render time. This one has already bitten: Homebrew's
  ffmpeg 8.1.2 is built without freetype, so a developer testing against `PATH`
  will not reproduce what a user with the bundled build sees. The caption
  integration test skips itself rather than passing vacuously when drawtext is
  absent.

## Sources

| target | source | why |
|---|---|---|
| `aarch64-apple-darwin` | [osxexperts.net](https://www.osxexperts.net/) ffmpeg 8.1 | genuinely static arm64; publishes a per-binary SHA-256 |
| `x86_64-pc-windows-msvc` | [BtbN/FFmpeg-Builds](https://github.com/BtbN/FFmpeg-Builds) `n8.1 win64-gpl` | the `-gpl` (not `-gpl-shared`, not another vendor's "full") variant |

Both are pinned by SHA-256 in `source_for()` inside the fetch script. BtbN
publishes to a rolling `latest` tag, so its archive hash changes when they
rebuild; the script stops and asks rather than accepting the new bytes. Re-pin
deliberately — read the new configure line first, then
`--update-checksums`.

**Open item before public release.** osxexperts.net labels its downloads "for
educational purposes only". That restriction cannot attach to GPL software, but
relying on a third-party binary whose publisher disclaims redistribution is a
weak position for a project that must carry a written source offer. Either build
the macOS sidecar from source in CI, or move to a source that publishes its
corresponding source alongside the binary. Flag this in the pre-launch legal
review.

## Wiring (not yet in `tauri.conf.json`)

Two things are needed before the sidecar can be spawned:

```jsonc
// tauri.conf.json -> bundle
"externalBin": ["binaries/ffmpeg"]
```

```jsonc
// src-tauri/capabilities/default.json -> permissions
{
  "identifier": "shell:allow-execute",
  "allow": [{ "name": "binaries/ffmpeg", "sidecar": true, "args": true }]
}
```

`"args": true` accepts any argument vector. Tighten it to a validator list once
the argv shape settles — the compositor is the only thing that builds these
arguments, and it is a pure function, so the set is enumerable.

## Verifying by hand

```sh
./ffmpeg-aarch64-apple-darwin -hide_banner -L        | head -4   # GPL, not nonfree
./ffmpeg-aarch64-apple-darwin -hide_banner -version  | grep configuration
./ffmpeg-aarch64-apple-darwin -hide_banner -encoders | grep 264  # h264_videotoolbox
./ffmpeg-aarch64-apple-darwin -hide_banner -filters  | grep -E 'drawtext|xfade|sidechaincompress'
```

To run the compositor's real-ffmpeg tests against a bundled sidecar rather than
whatever is on `PATH`:

```sh
hickeyfield_FFMPEG=$PWD/src-tauri/binaries/ffmpeg-aarch64-apple-darwin \
  cargo test -p hickeyfield-core --ignored
```
